# InterDash Cloud VPS Control Plane API (v1)

The **InterDash REST Control Plane API** is a secure, production-grade programmatic interface for managing virtual private servers (LXC containers on Proxmox VE), hypervisor nodes, user accounts, asynchronous lifecycle operations, support tickets, and platform configuration.

External automation engines, billing providers (e.g., WHMCS, Stripe webhooks), CI/CD pipelines, Discord bots, and infrastructure orchestrators can perform all platform actions without bypassing safety rails, locks, or audit systems.

---

## Key Principles & Architectural Guarantees

1. **Single Source of Truth**: The external REST API interacts directly with InterDash's canonical services (`VpsOperationsService`, `ProvisioningService`, `ProxmoxService`, `IpamService`, `VpsExpiryService`, `ApiKeyService`). There are no duplicate or shadow business paths.
2. **Zero Secret Leakage**: API response DTOs strictly scrub all secrets. Root passwords, Proxmox API tokens, client secrets, and credential hashes are never serialized in API responses or audit trails.
3. **Admin-Governed Credentials**: Only platform administrators can create, rotate, and revoke API keys via the InterDash Admin Portal (`/admin/settings?tab=api-keys`).
4. **Fine-Grained Least Privilege**: Keys can be granted granular capabilities (e.g., power controls only, read-only analytics, or ticket automation) rather than blanket root privileges. Keys can also be restricted to specific user accounts.
5. **Idempotent Operations**: All mutative operations support the `Idempotency-Key` header with SHA-256 payload integrity hashing to prevent duplicate provisioning or conflicting state changes.
6. **Unified Standard Envelopes**: All requests return standard envelopes with a traceable `X-Request-ID` header.

## Authentication & Credentials

All requests to `/api/v1/*` (except public discovery and documentation routes) require authentication using a Bearer API token.

```http
GET /api/v1/instances HTTP/1.1
Host: your-interdash-domain.com
Authorization: Bearer ih_live_9f83a2e1c0d4e5f67890123456789abc
Accept: application/json
```

### Security Invariants

- **Prefix Convention**: Live API keys always start with the prefix `ih_live_` followed by 32 cryptographically random alphanumeric characters (256 bits of entropy).
- **One-Time Secret Display**: When an API key is generated or rotated, the plaintext key is displayed **once**. InterDash stores only an irreversible **SHA-256 hash** of the key.
- **Constant-Time Verification**: Secret verification uses cryptographic constant-time comparison to prevent timing attacks.
- **Strict Transport Enforcement**: API tokens must **only** be supplied in the `Authorization: Bearer <token>` header. Keys supplied in query parameters (e.g., `?api_key=...`) or JSON request bodies are explicitly rejected with `400 INVALID_CREDENTIAL_TRANSPORT`.
- **Instant Revocation & Expiration**: Revoked keys or expired keys are immediately rejected on the next incoming request.

## Rate Limiting & Sliding Windows

InterDash implements sliding window rate limiting keyed by the authenticated API Key ID (with client IP fallback). Rate limits are partitioned by endpoint workload:

| Endpoint Class | Default Limit | Applicable Operations |
| :--- | :--- | :--- |
| **`standard`** | 120 req / min | Reads, listing, metadata updates, tickets, settings, analytics |
| **`heavy`** | 30 req / min | Instance power operations, OS reinstall, password reset, delete |
| **`provision`** | 10 req / min | Asynchronous LXC provisioning requests (`POST /api/v1/instances`) |

> **Note**: Custom per-minute rate limits can be configured on individual API keys by administrators in the Admin UI. The custom RPM applies to the `standard` endpoint class.

### Rate Limit Headers

Every API response includes current rate limit status:

| Header | Description |
| :--- | :--- |
| `X-RateLimit-Limit` | Maximum allowed requests within the current 60-second window |
| `X-RateLimit-Remaining` | Remaining requests available before hitting the rate limit |
| `X-RateLimit-Reset` | Time in seconds until the current sliding window resets |
| `Retry-After` | (Only on `429 Too Many Requests`) Seconds to wait before retrying |

When the limit is exceeded, the server returns HTTP `429 Too Many Requests`:

```json
{
  "error": {
    "code": "API_RATE_LIMITED",
    "message": "Rate limit exceeded for endpoint class 'heavy'. Try again in 24 seconds.",
    "details": {
      "endpointClass": "heavy",
      "limitRpm": 30,
      "retryAfterSeconds": 24
    }
  },
  "requestId": "3a64b912-21ef-4573-b295-88849b2940af"
}
```

## Idempotency Engine

To guarantee that network retries or timeouts do not cause duplicate instances or redundant power cycles, mutative endpoints support the `Idempotency-Key` HTTP header.

```http
POST /api/v1/instances HTTP/1.1
Host: your-interdash-domain.com
Authorization: Bearer ih_live_...
Idempotency-Key: e82b545e-49b8-4c12-b054-94c34a2e2d92
Content-Type: application/json

{
  "name": "Production Worker",
  "nodeId": "pve-node-01",
  "template": "local:vztmpl/ubuntu-22.04.tar.zst",
  "cpuCores": 2,
  "memoryMb": 4096,
  "diskGb": 40
}
```

### How Idempotency Works

1. **Header Required on Provisioning**: `POST /api/v1/instances` requires the `Idempotency-Key` header (max 128 characters).
2. **Payload Hash Verification**: The server calculates a deterministic SHA-256 digest of the sorted request body.
3. **Safe Replay**: If a request arrives with an `Idempotency-Key` that was already successfully processed for that API key, the server returns the cached response with an added header:
   ```http
   Idempotent-Replay: true
   ```
4. **Conflict Guard**: If an `Idempotency-Key` is reused with a different request body, path, or method, the server rejects it immediately with HTTP `409 Conflict` (`IDEMPOTENCY_CONFLICT`).

## Canonical Scope Registry

API keys are restricted to explicitly granted scopes. Scopes follow the `resource:action` convention.

| Scope | Category | Dangerous | Admin Only | Description |
| :--- | :--- | :---: | :---: | :--- |
| `api:full` | Wildcard | **Yes** | **Yes** | Full access across all control plane operations. Treat like root access. |
| `instances:read` | Instances | No | No | View instance details, IPs, specs, and status. |
| `instances:write` | Instances | No | No | Update instance names, descriptions, and reset passwords. |
| `instances:power` | Instances | No | No | Start, stop, and reboot VPS instances. |
| `instances:reinstall`| Instances | **Yes** | No | Wipe and reinstall instance OS with template selection. |
| `instances:delete` | Instances | **Yes** | No | Destroy instances and release IPAM allocations. |
| `instances:console`| Instances | No | No | Generate interactive terminal tickets and WebSocket sessions. |
| `instances:expiry` | Instances | No | **Yes** | Set, extend, or clear instance expiration dates. |
| `provisioning:read`| Provisioning | No | No | Inspect asynchronous provisioning jobs and step logs. |
| `provisioning:create`| Provisioning | **Yes** | **Yes** | Provision new virtual servers on Proxmox hypervisors. |
| `provisioning:cancel`| Provisioning | No | **Yes** | Abort in-flight or stalled provisioning jobs. |
| `nodes:read` | Nodes | No | **Yes** | View Proxmox cluster nodes, health, and storage pools. |
| `nodes:write` | Nodes | **Yes** | **Yes** | Register new nodes and update hypervisor configurations. |
| `nodes:verify` | Nodes | No | **Yes** | Run live connectivity and storage discovery tests on nodes. |
| `nodes:delete` | Nodes | **Yes** | **Yes** | Remove hypervisor nodes (with active instance safety check). |
| `tickets:read` | Tickets | No | No | View support tickets and discussion messages. |
| `tickets:write` | Tickets | No | No | Open tickets, post replies, and change ticket statuses. |
| `users:read` | Users | No | **Yes** | List user accounts and view profile metadata. |
| `users:write` | Users | **Yes** | **Yes** | Suspend, ban, or reactivate user accounts. |
| `users:role` | Users | **Yes** | **Yes** | Promote or demote user roles (`user`, `admin`, `owner`). |
| `settings:read` | Settings | No | No | Read platform branding, contact URLs, and auth configs. |
| `settings:write` | Settings | **Yes** | **Yes** | Update platform branding and authentication provider settings. |
| `analytics:read` | Analytics | No | No | Access real infrastructure telemetry and utilization stats. |
| `operations:read` | Operations | No | No | Query asynchronous lifecycle operations and step history. |
| `audit:read` | Audit | No | **Yes** | Search platform audit logs (scrubbed of sensitive data). |

## Error Handling & Error Codes

InterDash APIs return RFC 7807-compatible error envelopes with standardized machine-readable error codes.

### Common Error Codes

| HTTP Status | Error Code | Description |
| :---: | :--- | :--- |
| **400** | `INVALID_CREDENTIAL_TRANSPORT` | API key was passed in query parameter or request body instead of the `Authorization` header. |
| **400** | `INVALID_IDEMPOTENCY_KEY` | The `Idempotency-Key` header exceeds 128 characters or contains illegal formatting. |
| **400** | `IDEMPOTENCY_KEY_REQUIRED` | The endpoint requires an `Idempotency-Key` header (e.g., `POST /api/v1/instances`). |
| **400** | `HOSTNAME_CONFIRMATION_MISMATCH` | OS reinstall payload `confirmHostname` did not match the instance hostname. |
| **400** | `INVALID_PASSWORD` | Password does not meet security criteria (minimum 8 characters). |
| **401** | `API_KEY_REQUIRED` | Missing or blank `Authorization` header. |
| **401** | `INVALID_AUTHORIZATION_HEADER` | Authorization header is not formatted as `Bearer <token>`. |
| **401** | `INVALID_API_KEY` | API token not recognized, invalid checksum, or invalid hash. |
| **401** | `API_KEY_REVOKED` | API key has been revoked by an administrator. |
| **401** | `API_KEY_EXPIRED` | API key has reached its configured expiration date. |
| **403** | `INSUFFICIENT_SCOPE` | API key lacks one or more required scopes. |
| **403** | `ADMIN_ROLE_REQUIRED` | Operation requires administrator permissions. |
| **403** | `RESOURCE_FORBIDDEN` | Key is restricted to a user account that does not own this resource. |
| **404** | `INSTANCE_NOT_FOUND` | No VPS matches the requested ID. |
| **404** | `NODE_NOT_FOUND` | No hypervisor node matches the requested ID. |
| **404** | `JOB_NOT_FOUND` | Provisioning job not found. |
| **409** | `IDEMPOTENCY_CONFLICT` | `Idempotency-Key` reused with different parameters or payload. |
| **409** | `OPERATION_IN_PROGRESS` | VPS is locked by an existing in-flight operation. |
| **409** | `NODE_HAS_ACTIVE_INSTANCES` | Cannot delete hypervisor node because instances are still hosted on it. |
| **422** | `PREFLIGHT_STORAGE_UNSUPPORTED` | Selected storage pool does not support root container volumes. |
| **422** | `PREFLIGHT_TEMPLATE_NOT_FOUND` | Selected OS template does not exist on the node. |
| **422** | `PREFLIGHT_BRIDGE_INVALID` | Selected network bridge does not exist on the hypervisor. |
| **429** | `API_RATE_LIMITED` | Sliding window request quota exceeded. Check `Retry-After`. |
| **500** | `INTERNAL_SERVER_ERROR` | Unhandled error. Check `X-Request-ID` in server logs. |

### 2. TypeScript / Node.js (Fetch)

```typescript
import crypto from "node:crypto";

interface ApiResponse<T> {
  data: T;
  requestId: string;
}

interface InstanceDTO {
  id: string;
  name: string;
  status: "running" | "stopped" | "provisioning" | "error";
  ipv4Address: string;
}

export class InterDashClient {
  constructor(
    private readonly baseUrl: string,
    private readonly apiKey: string
  ) {}

  private async request<T>(
    path: string,
    options: RequestInit & { idempotencyKey?: string } = {}
  ): Promise<ApiResponse<T>> {
    const headers: Record<string, string> = {
      Authorization: `Bearer ${this.apiKey}`,
      Accept: "application/json",
      "Content-Type": "application/json",
      ...(options.headers as Record<string, string>),
    };

    if (options.idempotencyKey) {
      headers["Idempotency-Key"] = options.idempotencyKey;
    }

    const res = await fetch(`${this.baseUrl}${path}`, {
      ...options,
      headers,
    });

    const json = await res.json();
    if (!res.ok) {
      throw new Error(`[${json.error?.code || res.status}] ${json.error?.message || "API Error"}`);
    }

    return json;
  }

  public async listInstances(): Promise<InstanceDTO[]> {
    const res = await this.request<InstanceDTO[]>("/instances");
    return res.data;
  }

  public async rebootInstance(instanceId: string): Promise<string> {
    const res = await this.request<{ operationId: string }>(`/instances/${instanceId}/reboot`, {
      method: "POST",
    });
    return res.data.operationId;
  }

  public async provisionInstance(params: {
    name: string;
    nodeId: string;
    template: string;
    cpuCores: number;
    memoryMb: number;
    diskGb: number;
    rootPassword?: string;
  }): Promise<{ jobId: string; statusUrl: string }> {
    const idempotencyKey = crypto.randomUUID();
    const res = await this.request<{ jobId: string; statusUrl: string }>("/instances", {
      method: "POST",
      idempotencyKey,
      body: JSON.stringify(params),
    });
    return res.data;
  }
}
```

### 3. Python 3 (httpx / requests)

```python
import uuid
import httpx
from typing import Dict, Any, List

class InterDashClient:
    def __init__(self, base_url: str, api_key: str):
        self.base_url = base_url.rstrip("/")
        self.headers = {
            "Authorization": f"Bearer {api_key}",
            "Accept": "application/json",
            "Content-Type": "application/json",
        }

    def list_instances(self, status: str = None) -> List[Dict[str, Any]]:
        params = {}
        if status:
            params["status"] = status
        with httpx.Client() as client:
            resp = client.get(f"{self.base_url}/instances", headers=self.headers, params=params)
            resp.raise_for_status()
            return resp.json()["data"]

    def provision_instance(self, payload: Dict[str, Any]) -> str:
        headers = dict(self.headers)
        headers["Idempotency-Key"] = str(uuid.uuid4())
        with httpx.Client() as client:
            resp = client.post(f"{self.base_url}/instances", headers=headers, json=payload)
            resp.raise_for_status()
            return resp.json()["data"]["jobId"]

    def reboot_instance(self, instance_id: str) -> str:
        with httpx.Client() as client:
            resp = client.post(f"{self.base_url}/instances/{instance_id}/reboot", headers=self.headers)
            resp.raise_for_status()
            return resp.json()["data"]["operationId"]
```

### 4. Go (Golang)

```go
package main

import (
	"bytes"
	"encoding/json"
	"fmt"
	"net/http"
	"time"
)

type Client struct {
	BaseURL    string
	APIKey     string
	HTTPClient *http.Client
}

func NewClient(baseURL, apiKey string) *Client {
	return &Client{
		BaseURL: baseURL,
		APIKey:  apiKey,
		HTTPClient: &http.Client{
			Timeout: 15 * time.Second,
		},
	}
}

type APIResponse struct {
	Data      interface{} `json:"data"`
	RequestID string      `json:"requestId"`
}

func (c *Client) RebootInstance(instanceID string) error {
	url := fmt.Sprintf("%s/instances/%s/reboot", c.BaseURL, instanceID)
	req, err := http.NewRequest(http.MethodPost, url, nil)
	if err != nil {
		return err
	}

	req.Header.Set("Authorization", "Bearer "+c.APIKey)
	req.Header.Set("Accept", "application/json")

	resp, err := c.HTTPClient.Do(req)
	if err != nil {
		return err
	}
	defer resp.Body.Close()

	if resp.StatusCode >= 400 {
		return fmt.Errorf("API error: status %d", resp.StatusCode)
	}

	return nil
}
```
